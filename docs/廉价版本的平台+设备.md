# 廉价版本的平台与设备方案

## 1. 结论

1. **M20 可以换成四轮小车**。优先选择成品的四轮差速/四轮滑移转向底盘；它与当前 Nav2 的 `linear.x + angular.z` 控制方式最接近，改动最小。
2. **M20 并不是“只输入 `/NAV_CMD` 就完成全部底盘能力”**。当前算法侧确实主要通过 `/NAV_CMD` 向 M20 下发速度，但 M20 厂商节点还隐藏完成了电机闭环、通信、急停、失联停车和底盘状态管理。普通四轮车通常不认识 `drdds/msg/NavCmd`，必须具有 ROS 2 底盘驱动或增加一个 `/cmd_vel` 到底盘协议的适配节点。
3. 为最大限度支持现有算法，廉价版仍保留 **Livox MID360 + MID360 内置 IMU + 海康工业相机**。不建议在第一版同时替换底盘和传感器型号。
4. 当前仓库推荐下限是 **Jetson Orin NX 16GB**。现有算法没有被 64GB 显存硬绑定；廉价版 A/B 档选 Orin NX 16GB，C 档可选 AGX Orin 32GB。只有长期同时运行大地图建图、RViz、录包和多个 AI 模型时，才考虑 AGX Orin 64GB。
5. 推荐采购 **B 档**：成品差速底盘、Orin NX 16GB 工业盒、原型号传感器和预留集成预算，预计约 **3.81 万元**。

> 本文价格为 2026-09 的调研预算，不是正式报价。京东部分页面动态展示 SKU 和价格，采购前必须让商家出具包含型号、配件、发票、装配及售后的书面报价。三档均按单台 MID360 估算。

## 2. 为什么优选四轮差速底盘

当前控制链为：

```text
Nav2 controller_server
  -> /cmd_vel_nav
  -> velocity_smoother
  -> /cmd_vel
  -> M20 Adapter
  -> /NAV_CMD (Domain 42)
  -> nav_cmd_domain_bridge
  -> /NAV_CMD (Domain 0)
  -> M20 厂商底盘节点
```

当前 Nav2 参数已经是非全向模式：

```yaml
max_vel_y: 0.0
vy_samples: 1
```

因此各类底盘的适配优先级是：

| 底盘形式 | 可行性 | 对当前算法的影响 | 建议 |
|---|---|---|---|
| 四轮差速/滑移转向 | 高 | 直接使用 `vx + wz`，可原地转向 | **首选** |
| 两轮差速加万向轮 | 高 | 控制最简单，但承载和越障一般 | 仅适合低预算室内验证 |
| 麦克纳姆四轮 | 中 | 可以先按 `vy=0` 当差速车使用；若要横移，需启用 `vy` 并校准运动学 | 不是第一选择 |
| 阿克曼四轮 | 低 | 不能直接把角速度当转角，需转向角转换、最小转弯半径及规划参数适配 | 第一版不选 |

底盘建议满足：

- 成品装配发货，带电池、充电器、电机驱动器、编码器和底盘控制板。
- ROS 2 Humble 可用，或至少公开串口/CAN 协议及 Linux SDK。
- 能稳定接收 `geometry_msgs/msg/Twist` 的 `/cmd_vel`；最好提供 `/odom` 和 TF。
- 有硬件急停、遥控接管和命令超时自动停车，超时建议不大于 0.5 秒。
- 额定载荷至少 20 kg，建议 30 kg 以上；上层需承载 Orin、MID360、相机、支架、电源和线束。
- 顶板有标准安装孔，商家可按图安装传感器立柱和算力盒。
- 室内方案建议车宽约 45～60 cm、可原地旋转；轮径和离地间隙根据门槛环境确认。

## 3. `/NAV_CMD` 是否是唯一要求

### 3.1 对现有 M20

从当前算法仓库的直接控制输出看，M20 主要接收：

```text
/NAV_CMD [drdds/msg/NavCmd]
  data.x_vel
  data.y_vel
  data.yaw_vel
```

现有 Adapter 将 `/cmd_vel` 转成 `/NAV_CMD`，跨域桥再从 Domain 42 转发到 Domain 0。但这只说明**算法到 M20 的控制入口**主要是 `/NAV_CMD`，不代表整车只需实现这一个 Topic。

### 3.2 对廉价四轮车

廉价车应保留标准接口：

```text
FAST-LIVO + 定位 + Nav2
  -> /cmd_vel
  -> chassis_adapter（新增外围适配层）
  -> 串口、CAN 或厂商 ROS 2 底盘驱动
  -> 四轮底盘
```

最小适配工作包括：

- 将 `/cmd_vel.linear.x` 和 `/cmd_vel.angular.z` 转成目标底盘协议。
- 设置速度、加速度、角速度和死区限制。
- 在底盘控制器中实现命令 watchdog，ROS 节点退出或链路断开时自动发零速。
- 接入硬件急停和遥控接管；软件急停不能替代硬件急停。
- 发布编码器里程计 `/odom` 供验收和故障排查。当前 FAST-LIVO 主定位链未必强依赖轮速里程计，但不应购买无编码器底盘。
- 若底盘节点放在 Domain 0，需桥接 `/cmd_vel` 或底盘私有消息；也可将底盘驱动放在 Domain 42，省去当前 M20 专用 `/NAV_CMD` 跨域链。

不建议让新车刻意仿造 `drdds/msg/NavCmd`。保留标准 `/cmd_vel` 并新增独立适配节点，风险更低，也不需要改 FAST-LIVO、定位和 Nav2 核心代码。

## 4. 传感器配置与算法兼容性

为复用当前代码，三档均采用：

| 设备 | 保留原因 | ROS 2 输入 |
|---|---|---|
| Livox MID360 | 当前 FAST-LIVO、驱动和点云参数均针对该型号 | `/livox/lidar` |
| MID360 内置 IMU | 当前 VIO/LIO 链直接使用 | `/livox/imu` |
| 海康工业相机 + 原规格镜头 | 当前已有 `mvs_ros_driver`、内参和雷达—相机标定流程 | `/left_camera/image` |

`/rgb_img` 是 FAST-LIVO 派生图像，`/scan` 是 `/cloud_registered` 转换出的虚拟 2D LaserScan，不需要额外购买 2D 雷达。

更换底盘和支架后，即使传感器型号一致，也必须处理：

1. 重测并标定 `T_lidar_base`，不能照搬 M20 的安装位姿。
2. 相机与 MID360 使用同一刚性支架时，原 `T_camera_lidar` 可作为初值，但仍需重新标定验收。
3. `T_imu_lidar` 属于 MID360 内部关系，通常可沿用对应设备标定值。
4. 按新车外形修改 Nav2 的 `footprint`；当前约为 `0.820 m × 0.506 m`，不能直接用于尺寸不同的小车。
5. 重新标定最大速度、角速度、加减速度和最小速度死区。
6. 根据 MID360 新安装高度验证 `/scan` 的点云切片范围；当前是 `-0.3 m ～ 0.5 m`。
7. Orin 上重新编译 ARM64 工作区，不能复制当前 `build/`、`install/` 中的 x86_64 产物。
8. 海康 SDK 在 ARM64 下核对 `libusb` 预加载，ROS 2 通信沿用仓库的 FastDDS UDP-only 配置。

## 5. A/B/C 三档预算

### 5.1 共用预算口径

- 保留单台 MID360、海康工业相机及镜头。
- 优先采购成品整车或商家完成机械、电气安装的底盘。
- 预算包含必要线材、供电转换、交换机、急停和安装调试余量。
- 不包含显示器、键鼠和独立开发电脑；RViz 可通过远程工作站查看。
- 不将超低价亚克力教学车列入方案：其负载、刚度、制动、续航和电气安全不适合承载 MID360 与 Orin。

## 7. 下单前向商家确认的问题

### 7.1 底盘

1. 是完整成品还是散件？是否能安装客户提供的 Orin、MID360、相机和急停？
2. 是否支持 Ubuntu 22.04、ROS 2 Humble 和 ARM64？驱动源码能否交付？
3. 原生控制 Topic 是否为 `/cmd_vel`，消息是否为 `geometry_msgs/msg/Twist`？
4. 若使用串口/CAN，是否提供公开协议、CRC 说明和 C++/Python Linux 示例？
5. 是否发布编码器 `/odom`、`joint_states` 和 TF？坐标轴是否符合 REP-103？
6. 额定/峰值载荷、尺寸、轮径、离地间隙、最大坡度和最小通道宽度是多少？
7. 命令断开多少毫秒后自动停车？硬件急停是否直接切断电机使能？
8. 电池电压、容量、连续放电能力、续航和充电时间是多少？能否为 Orin 和传感器预留独立电源？
9. 能否提供电气图、接口定义、SDK、固件及 ROS 2 示例包？
10. 是否支持备轮、电机、驱动器、电池单独采购及至少一年售后？

### 7.2 Orin 盒子

1. 明确是 Orin Nano、Orin NX 16GB、AGX Orin 32GB 还是 AGX Orin 64GB，不能只看商品标题。
2. 核心模组是量产版还是开发版，载板型号和 JetPack 版本是什么？
3. 是否包含 NVMe、散热风扇、电源、Wi-Fi/蓝牙天线；是否支持掉电保护？
4. 至少需要两个稳定网口或一个网口加独立千兆交换机，以连接 MID360 和调试网络。
5. 宽压输入范围、峰值功耗及接插件型号是什么？是否能由底盘电池稳定供电？

### 7.3 MID360 和相机

1. MID360 是否全新正品、可开票、有序列号和官方保修？是否包含一分三线及适配电源？
2. 相机完整型号、接口、彩色/黑白、全局快门、镜头和线材是否与当前设备一致？
3. 商家是否能提供刚性支架 CAD/孔位图，确保安装后不松动、不遮挡雷达视场？

## 8. 到货验收与软件适配顺序

1. 只启动底盘，验证遥控、急停、失联停车、编码器方向和 `/cmd_vel` 正负方向。
2. 在 Domain 42 验证 `/cmd_vel` 到新底盘的适配节点；先限速到 `0.2 m/s` 和 `0.3 rad/s`。
3. 安装 MID360 与相机，确认供电、网口、时间戳和三个原始 Topic。
4. 完成相机内参、`T_camera_lidar` 和 `T_lidar_base` 标定。
5. 修改 footprint、速度/加速度、死区和 `/scan` 高度切片。
6. 分别验证 FAST-LIVO、2D 定位、Nav2，再进行完整并发压力测试。
7. 最后才逐步提高速度；确认急停、ROS 节点退出和网线断开时均能停车。

## 9. 最终采购建议

- **首选 B 档**，并优先向 S100/S300 同级差速服务底盘商家询价“无主控、保留完整底盘控制器、电池、急停，由商家装好传感器支架和 Orin 盒”的整机方案。
- A 档适合实验室先做算法迁移验证；C 档适合需要更大载荷、续航和并发算力的长期平台。
- 在确认现有海康相机完整型号、实际整机载荷和运行任务并发量之前，不应直接下单。
- 四轮车可以复用当前 FAST-LIVO、定位、Nav2 和 RViz 主链，但无法复刻 M20 的地形通过性；本方案定位是平地轮式平台，不是低价等价机器狗。

## 10. 两个极限降本方案

### 10.1 先说明价格边界

若要求保留 `MID360 + 海康工业相机 + FAST-LIVO + Orin`，整机不可能压到 5,000 元；仅 MID360 或 Orin 主控的正常采购价就可能超过该总预算。极限降本必须把目标从“兼容当前完整算法链”调整为“实现室内平地 2D 建图、定位和导航”。

两个极限方案的定位如下：

| 项目 | 方案一：5,000 元开放 ROS 2 车 | 方案二：约 1,000 元消费扫地机 |
|---|---|---|
| 目标 | 可二次开发的 2D SLAM/Nav2 实验车 | 最低成本获得成品建图导航功能 |
| 预算 | 约 4,500～5,000 元 | 约 700～1,200 元 |
| 开放 ROS 2 | **是**，采购前必须确认驱动或串口协议 | **通常否**，按封闭产品看待 |
| 标准 `/cmd_vel`、`/scan`、`/odom` | 可以要求具备 | 通常不对外提供 |
| 自主建图与定位 | 可以，使用 2D 激光方案 | 可以，但只在厂商 App/固件内使用 |
| Nav2 与 RViz | 可以 | 通常不可以 |
| 当前航点管理等通用 ROS 2 节点 | 可适配复用 | 不可直接复用 |
| FAST-LIVO/当前 3D 定位链 | **不可运行** | **不可运行** |
| 当前仓库完整兼容 | 否，只能复用导航层通用代码 | 否 |

### 10.2 方案一：5,000 元内开放 ROS 2 极限车

这是两个方案中唯一适合继续开发当前项目的选择。建议直接购买带编码器、电池和底盘控制板的成品两轮/四轮差速教学底盘，不购买 MID360、工业相机和 Orin。

| 项目 | 极限规格 | 目标预算（元） |
|---|---|---:|
| 成品差速底盘 | 金属底盘、编码器电机、控制板、电池、充电器，优先原生 `/cmd_vel` 和 `/odom` | 1,800 |
| 主控 | Intel N100，8GB 内存、128/256GB SSD；选择准系统或二手小主机 | 1,200 |
| 2D 激光雷达 | YDLIDAR X3 Pro/T-mini Plus 或 RPLIDAR C1 同级，要求 Linux ROS 2 驱动 | 350 |
| 供电 | 主控 DC-DC、保险丝、独立开关和接插件 | 450 |
| 安全与安装 | 急停、雷达支架、顶板、线材 | 500 |
| 运费与返工余量 | 驱动板、轮胎、电池容量或接口不符的余量 | 500 |
| **目标合计** | 不含显示器、键鼠和开发电脑 | **4,800** |

采购策略：先向教学 ROS 小车商家询问“无树莓派、保留完整底盘电控和电池”的成品 SKU，再自行安装 N100 和低价雷达。公开页面的最低价格经常是不含主控、雷达或电池的基础 SKU，必须按完整清单确认。

建议软件链改为：

```text
2D 激光雷达 -> /scan
底盘编码器 -> /odom + odom TF
slam_toolbox -> 2D 建图
AMCL 或 slam_toolbox localization -> map -> odom
Nav2 -> /cmd_vel -> 底盘驱动
```

可以保留或适配：

- ROS 2 Humble、RViz、Nav2、地图保存和标准 `/cmd_vel` 控制框架。
- 航点添加/撤销/清空等与传感器无关的通用逻辑。
- 导航进度功能，但实际轨迹输入需要改为 `/odom` 或新的 2D 定位轨迹 Topic。
- Domain 42 可继续作为算法域；若底盘驱动也运行在 Domain 42，就不再需要 M20 的 `/NAV_CMD` 跨域桥。

必须停用或替换：

- FAST-LIVO、Livox 驱动、`/livox/lidar`、`/livox/imu` 和 `/cloud_registered`。
- 海康相机驱动、视觉词典以及雷达—相机外参链。
- 当前基于 3D 定位结果生成的 TF 与红色历史轨迹链。
- M20 专用 `drdds/msg/NavCmd` Adapter 和 `nav_cmd_domain_bridge`。

性能边界：仅建议室内平地、低速运行，初始限制约 `0.2 m/s`、`0.3 rad/s`。低价雷达对黑色、玻璃、强光和低矮障碍物识别较弱；无深度相机时，桌沿、悬空和三维障碍不能可靠感知。N100 适合 2D SLAM + Nav2 + RViz，不能据此承诺完整 FAST-LIVO 与 AI 模型并发。

### 10.3 方案二：约 1,000 元封闭式 LDS 扫地机器人

选择米家、科沃斯、海尔等促销价约 700～1,200 元、明确标注 LDS 激光导航的成品扫地机器人。它通常已包含底盘、电池、充电座、LDS、电机控制器、碰撞传感器、悬崖传感器和厂商建图导航固件，开箱即可通过 App 建图、分区和回充。

| 项目 | 预算（元） |
|---|---:|
| 带 LDS 建图的成品扫地机器人 | 700～1,000 |
| 可选耗材或二手调试机余量 | 0～200 |
| **合计** | **约 700～1,200** |

该方案满足的是“低价成品能够自主建图导航”，不满足“廉价替代当前 ROS 2 研发平台”。采购时应默认以下接口均不存在：

```text
SSH/root
Ubuntu 22.04
ROS 2 Humble
/scan
/odom
/cmd_vel
厂商底盘协议和驱动源码
外接传感器与部署当前仓库的能力
```

只有商家书面确认开放本地 SDK、底盘控制、地图数据和传感器数据时，才可把某个具体机型视为二次开发候选；依赖破解、刷机或云端逆向的型号不应作为项目交付方案。固件更新后接口失效、设备变砖及合规问题也无法验收。

约 1,000 元自行拼装开放 ROS 小车理论上可以由二手树莓派/低端 ARM 板、亚克力底盘和低价雷达组成，但预算几乎没有留给电池保护、编码器质量、急停、支架和返工，且通常不是成品。因此它只适合课堂演示，不作为本项目推荐方案。

### 10.4 为什么扫地机器人不到 1,000 元也能建图

1. 消费产品销量大，模具、主板、算法和供应链成本被大量摊薄；科研小车通常是小批量产品。
2. 扫地机采用低成本定制 LDS、专用 SoC 和一体化主板，不需要通用 Orin、工业相机或 MID360。
3. 场景被严格限定为室内平地、低速清扫，功能和传感器只需满足单一产品目标。
4. 固件、地图和 App 通常封闭，不承担 ROS 2 Topic、驱动源码、通用 SDK、外部设备接入和科研售后成本。
5. “厂商固件内部可以建图”与“能够输出原始传感器数据并运行本仓库算法”是两个不同指标。

### 10.5 极限方案结论

- 若目标是继续修改和验证 ROS 2 代码，最低建议选择 **方案一**，并接受算法降级为 2D 激光 SLAM + Nav2；建议把 5,000 元视为采购上限而不是可靠工程产品的常规价格。
- 若目标只是展示“机器可以建图并自主移动”，选择 **方案二** 最便宜，但它是独立消费产品，不能接替 M20，也不能作为当前仓库的软件验证平台。
- 若仍要求原样运行 `MID360 + 海康 + FAST-LIVO`，应继续采用前述 2.75 万元以上方案，不应以扫地机器人售价作为同口径成本基准。
