# 需求 01：导航地图形态与下发

## 一、需求怎么理解？

**问：产品所说“用户上传 A 狗的 3 楼建图地图，下发到 B 机器狗，在平台下发 B 的导航任务”具体是什么？**

答：这是一个“跨机器狗复用地图”的需求：同为 M20 的 A 狗负责在 3 楼采集和建图，平台保存 A 狗生成的地图包；同为 M20 的 B 狗不重新建图，而是下载并激活这套地图，使用 B 狗自身的激光雷达、摄像头和 IMU 在 A 狗建立的全局坐标系中完成重定位，定位成功后再执行平台下发给 B 狗的导航任务。

这里的“地图”不应理解为一张图片，也不应只理解为 ROS 2 Bag。结合当前代码库，它是一套由 A 狗同一次建图生成、整体版本化和整体下发的地图包，至少同时服务于 B 狗的 3D 重定位、2D 地图发布和 Nav2 路径规划。典型业务流程是：

```text
A 狗（M20）在 3 楼使用激光雷达、摄像头和 IMU 采集数据
  -> 实时建图或录制 Bag 后离线建图
  -> 生成 3D 地图、2D 栅格地图和重定位数据库
  -> 将 A 狗生成的完整地图包上传到平台
  -> 平台把指定地图版本下发到 B 狗（M20）
  -> B 狗校验设备兼容性、文件完整性并激活地图
  -> B 狗启动自身雷达、摄像头、IMU 和 2D/3D 定位
  -> B 狗在 A 狗地图的 map 坐标系中完成重定位
  -> 平台下发绑定该地图 ID 和版本的 B 狗导航任务
  -> B 狗规划路径并执行任务
```

“浙大 4 楼地图”和“3 楼地图”应该被视为两个不同的地图 ID；每个地图 ID 可以再有多个版本。平台下发 B 狗导航任务时必须同时指定 B 狗 ID、地图 ID 和地图版本，不能只发送一组 `(x, y)` 坐标。

**问：A 狗和 B 狗都是 M20，A 狗的地图可以直接给 B 狗使用吗？**

答：从地图数据形态上可以跨狗下发，但不能仅凭“都是 M20”就认定可以无条件直接使用。M20 型号相同只说明机械和传感器方案大概率相近；地图能否复用，取决于 A、B 两狗的实际传感器配置、安装位姿、标定和运行参数是否兼容，以及 B 狗能否在 A 狗地图中稳定重定位。

需要重点比较：

| 检查项 | 为什么影响跨狗使用 |
|---|---|
| 激光雷达型号、扫描模式、点云格式和安装位置 | B 狗实时点云需要与 A 狗生成的 `map_3d.pcd` 和 Scan Context 特征保持相近 |
| IMU 型号、轴向、安装角度、噪声和时间同步 | FAST-LIVO 前端依赖 IMU 完成姿态传播，差异会造成里程计漂移和点云畸变 |
| 摄像头型号、分辨率、镜头和内参 | 视觉重定位使用 A 狗建立的 ORB 描述符，B 狗图像外观和投影模型差异过大会降低匹配率 |
| 相机—雷达外参 `T_camera_lidar` | 决定图像与点云融合、彩色地图和视觉约束的一致性 |
| IMU—雷达外参 `T_imu_lidar` | 决定惯导传播与雷达坐标的统一 |
| 雷达—车体外参 `T_lidar_base` | 影响 2D 栅格高度切片、车体坐标和导航安全边界 |
| 时间戳和硬件同步方式 | 不同步会使运动中的点云、图像和 IMU 无法正确对齐 |
| `device_parameters.yaml`、固件和软件版本 | 话题、帧名、滤波、分辨率及算法行为必须兼容 |

跨狗使用时，地图包仍使用 A 狗建图时的全局地图和描述符；B 狗运行前端时应使用经过标定的 **B 狗自身设备参数**。不能简单把 A 狗的全部标定参数覆盖到 B 狗上。平台应同时保存 A 狗建图参数摘要和 B 狗当前参数摘要，并按兼容规则判断是否允许激活。

**问：满足什么条件时，可以认为 A 狗地图可直接部署给 B 狗？**

答：建议至少满足以下条件：

1. A、B 都是同一硬件配置版本的 M20，雷达、摄像头、IMU 型号和安装结构一致。
2. 两台狗分别完成标定，关键外参差异处于项目允许的工程阈值内。
3. 使用相同 ROS 话题类型、坐标系约定、传感器模式和时间同步方案。
4. B 狗在 3 楼现场使用 A 狗地图完成多位置、多朝向冷启动重定位测试。
5. B 狗的 `/localization_status` 稳定为真，点云与 `map_3d.pcd` 对齐无明显重影。
6. B 狗加载 `map_2d` 后能规划路径，实机低速验证无系统性位置偏差。

因此，“同为 M20”是跨狗复用的有利前提，但不是充分条件。未经 B 狗现场重定位和导航验收的地图，只能标记为“可部署候选”，不能直接标记为“生产可用”。如果视觉差异导致 B 狗无法使用 A 狗的视觉描述符，可以先关闭视觉重定位，以雷达 Scan Context + ICP 验证跨狗能力；但这会降低某些重复结构场景中的辨识能力，需要单独评估。

## 三、地图是如何从 Bag 生成的？

**问：这个项目是直接把 `.db3` 转换成 PCD 和 PGM 吗？**

答：不是。项目采用“回放 Bag → 重跑 SLAM → 后端优化 → 退出时导出地图”的 ROS 2 流程：

```text
ros2 bag play
  -> /livox/lidar + /livox/imu + /left_camera/image
  -> fast_livo/fastlivo_mapping
  -> /cloud_registered + /aft_mapped_to_init
  -> mapping/lidar_loop_node + mapping/visual_loop_node
  -> 关键帧、回环、GTSAM/iSAM2 位姿图优化
  -> 停止建图后端
  -> map_3d.pcd + map_2d.pgm/yaml + 重定位数据库
```

关键入口如下：

- SLAM 前端：`fast_livo/launch/frontend.launch.py`。
- 建图后端：`mapping/launch/backend_mapping.launch.py`。
- 地图保存：`mapping/src/map_paving_engine.cpp`。
- 建图节点退出保存：`mapping/src/lidar_loop_node.cpp` 的析构流程。
- 栅格参数：`config/nav_parameters.yaml`。

**问：3D 地图具体怎么生成？**

答：建图后端保存每个关键帧局部点云，并持续优化关键帧位姿。停止 `lidar_loop_node` 时，`MapPavingEngine::buildAndSaveMaps()` 使用优化后的位姿，把所有关键帧变换到全局坐标系并拼接：

- 保存完整 RGB 字段点云为 `map_3d.pcd`。
- 过滤灰度回退点后保存真彩点云为 `map_3d_colored.pcd`。

在线定位实际加载的是 `map_3d.pcd`，彩色版本主要用于展示。

**问：2D 栅格地图具体怎么生成？**

答：不是调用 `nav2_map_server` 的保存服务，而是建图后端自行把 3D 关键帧转换为二维栅格：

1. 使用 `T_lidar_base` 把点转换到车体坐标。
2. 按相对地面的高度范围截取障碍层。
3. 对点云体素降采样和半径去噪。
4. 投影到 XY 平面。
5. 写出 `map_2d.pgm`。
6. 写出配套 `map_2d.yaml`。

当前主要参数为：

```yaml
pcd2pgm_map_resolution: 0.05
pcd2pgm_thre_z_min: -0.2
pcd2pgm_thre_z_max: 0.4
pcd2pgm_thre_radius: 0.8
pcd2pgm_thres_point_count: 10
```

这些参数位于 `config/nav_parameters.yaml`。其中高度切片和 `T_lidar_base` 会显著影响楼面、桌椅、墙体是否被正确投影为障碍。

**问：项目中有没有修改地图的代码？**

答：有“生成和过滤地图”的代码，但没有完整的交互式地图编辑器：

- `mapping/src/map_paving_engine.cpp`：控制 3D 拼图、Z 高度切片、滤波、2D 投影和 PGM/YAML 输出。
- `config/nav_parameters.yaml`：可调整 2D 分辨率、高度切片、滤波参数和雷达到车体外参。
- `data/map_2d.pgm`：本质是灰度图，可使用图像工具人工修补障碍和自由区，但必须保持尺寸不变并谨慎处理坐标含义。
- `data/map_2d.yaml`：可修改分辨率和原点，但修改后所有平台航点坐标都会受影响，不应在任务已录入后随意修改。
- `data/map_3d.pcd`：可用 CloudCompare、PCL 等外部工具裁剪或去噪，但若改动坐标系，必须同步处理重定位数据库，否则会造成地图与描述符不一致。

代码中没有发现成熟的网页地图编辑、禁行区绘制、地图版本合并或 PCD 修改后重建 Scan Context/视觉描述符的产品功能。

## 四、如何把指定 Bag 转成地图？

**问：`bag_20260607_173905` 应该怎样转换成 3D 和 2D 地图？**

答：推荐使用独立输出目录，不能直接使用现有 `data/`，也不要把输出目录设为 Bag 目录。建图节点启动时会删除目标目录中的 `*.pcd`、`*.pgm`、`*.yaml`、`*.txt`、`*.bin` 以及 `Scans/`、`Image/`；选错目录可能删除现有地图或 Bag 元数据。

建议目录：

```bash
mkdir -p /home/ubuntu/Desktop/ROS2_szs/DeepRobotics_ws/maps/bag_20260607_173905
cp /home/ubuntu/Desktop/ROS2_szs/DeepRobotics_ws/data/orb_vocabulary.dbow3 \
   /home/ubuntu/Desktop/ROS2_szs/DeepRobotics_ws/maps/bag_20260607_173905/
```

每个终端先加载同一环境：

```bash
cd /home/ubuntu/Desktop/ROS2_szs/DeepRobotics_ws
source /opt/ros/humble/setup.bash
source install/setup.bash
export ROS_DOMAIN_ID=42
```

终端 1 启动前端：

```bash
ros2 launch fast_livo frontend.launch.py \
  rviz:=false \
  params_file:=/home/ubuntu/Desktop/ROS2_szs/DeepRobotics_ws/config/device_parameters.yaml \
  use_sim_time:=true
```

终端 2 启动建图后端，目录末尾保留 `/`：

```bash
ros2 launch mapping backend_mapping.launch.py \
  map_save_dir:=/home/ubuntu/Desktop/ROS2_szs/DeepRobotics_ws/maps/bag_20260607_173905/ \
  use_sim_time:=true \
  rviz:=false
```

终端 3 回放 Bag：

```bash
ros2 bag play \
  /home/ubuntu/Desktop/ROS2_szs/DeepRobotics_ws/data/bags/bag_20260607_173905 \
  --clock \
  --remap /tf:=/tf_bag_garbage /tf_static:=/tf_static_bag_garbage
```

Bag 播放完成后：

1. 等待数秒，让后端处理队列和优化线程追上。
2. 对终端 2 的建图后端发送 `Ctrl+C`。
3. 等待退出日志显示地图保存完成。
4. 再停止前端。

最终应检查：

```bash
ls -lh /home/ubuntu/Desktop/ROS2_szs/DeepRobotics_ws/maps/bag_20260607_173905/
head -n 1 /home/ubuntu/Desktop/ROS2_szs/DeepRobotics_ws/maps/bag_20260607_173905/sc_database.txt
```

至少应存在：

```text
map_3d.pcd
map_2d.pgm
map_2d.yaml
sc_database.txt
visual_descriptors.bin
orb_vocabulary.dbow3
```

`sc_database.txt` 首行应大于 0。还应分别启动 3D 定位和 2D 定位验证，而不能只以“文件生成了”作为地图合格标准。

**问：能不能直接通过 GUI 完成？**

答：可以。当前 GUI 的流程是：

1. 启动控制台。
2. 点击“设置地图存放/读取目录”，选择一个新的空目录。
3. 点击“单次建图”。
4. 等待核心状态 Ready。
5. 点击“选择并播放数据包”，选择直接包含 `metadata.yaml` 和 `.db3` 的 Bag 目录。
6. 回放完成后点击“停止节点”，触发后端析构保存地图。

必须强调：新建图要选择新的输出目录。不要在当前生产地图目录中直接开始建图。

## 五、什么文件应该上传和下发？

**问：平台只下发 `map_2d.pgm` 和 YAML 可以吗？**

答：如果只是给 Nav2 Map Server 显示静态地图，并且定位由其他系统提供，可以。但当前代码库的 2D 定位不是纯 2D AMCL：它仍依赖 3D 点云地图和雷达/视觉重定位数据库。因此产品要支持当前完整的 2D 定位和导航，不能只下发 PGM/YAML。

**问：当前代码库下，完整导航地图包至少应包含什么？**

答：当前启用视觉融合时，建议至少整体下发：

```text
map_3d.pcd
map_2d.pgm
map_2d.yaml
sc_database.txt
visual_descriptors.bin
orb_vocabulary.dbow3
```

可选文件：

```text
map_3d_colored.pcd
aruco_landmarks.yaml
optimized_poses.txt
odom_poses.txt
times.txt
Scans/
Image/
```

其中 `map_3d_colored.pcd`、轨迹、`Scans/`、`Image/` 主要用于展示、诊断和离线复盘，不是在线导航的最小依赖。

**问：为什么这些文件必须整体下发？**

答：它们来自同一批关键帧，关键帧索引和位姿相互关联：

- `map_3d.pcd` 是 ICP 的全局先验地图。
- `sc_database.txt` 保存雷达描述符和历史位姿。
- `visual_descriptors.bin` 的帧顺序依赖同一关键帧序列。
- `map_2d.pgm/yaml` 与 3D 地图使用同一全局坐标原点。

混用不同建图批次的文件，可能出现“能加载但定位到错误位置”的危险情况。因此地图包必须不可拆分地版本化，并为每个文件保存 SHA-256。

**问：平台地图包建议是什么形态？**

答：建议采用：

```text
zju-building-floor-3/
└── 2026.06.07-001/
    ├── manifest.json
    ├── map_3d.pcd
    ├── map_2d.pgm
    ├── map_2d.yaml
    ├── sc_database.txt
    ├── visual_descriptors.bin
    ├── orb_vocabulary.dbow3
    └── optional/
```

Manifest 至少记录：地图 ID、版本、楼层、A 狗 ID、A 狗型号、A 狗建图传感器与标定摘要、允许部署的 M20 硬件配置版本、坐标系、分辨率、原点、文件哈希、视觉是否启用、ROS 版本、生成来源和兼容的软件版本。B 狗激活时还应把自身设备配置哈希与兼容规则进行比较，并记录本次跨狗部署关系。

B 狗应把地图下载到暂存目录，先校验全部文件，再检查自身 M20 硬件配置和标定兼容性，最后原子切换 `current` 软链接；不能直接覆盖正在使用的地图目录。

## 六、当前定位与导航怎么使用地图？

**问：3D 定位加载哪些地图文件？**

答：`localization/launch/backend_localization_3d.launch.py` 从同一个 `map_save_dir` 加载：

- `map_3d.pcd`
- `sc_database.txt`
- `visual_descriptors.bin`
- 视觉节点还需要 `orb_vocabulary.dbow3`

雷达定位通过 Scan Context 给出初始候选；视觉定位通过 ORB/DBoW3 给出候选；随后全局定位节点进行 ICP 和持续跟踪。

**问：2D 定位与导航加载哪些地图文件？**

答：`backend_localization_2d.launch.py` 仍启动完整的 3D 重定位链路，另外启动 Nav2 Map Server 加载：

```text
<map_save_dir>/map_2d.yaml
```

YAML 再通过相对路径加载同目录的 `map_2d.pgm`，地图发布到 `/map_2d`。Nav2 全局代价地图在 `config/nav_parameters.yaml` 中订阅 `/map_2d`。

**问：平台应该怎样下发导航任务？**

答：当前项目没有 HTTP/MQTT/WebSocket 等平台接口，也没有标准 Nav2 `NavigateThroughPoses` 完整链路。对于“A 狗建图、B 狗执行”的需求，平台任务至少要绑定 `targetRobotId=B`、地图 ID 和地图版本，并在 B 狗确认激活该版本且定位成功后才允许投递。现有 ROS 2 实现使用自定义多航点节点：

- `/clicked_point`：增加一个地图坐标系航点。
- `/waypoint_sequence/clear`：清空任务。
- `/waypoint_sequence/undo`：撤销航点。
- `/waypoint_sequence/pause`：暂停。
- `/waypoint_sequence/resume`：恢复。
- `/waypoint_sequence/status`：字符串状态。
- `waypoints_pose_array`：当前航点列表。

该节点逐段调用 Nav2 `ComputePathToPose`，发布 `/global_path`；后续自定义规划和控制链路生成 `/local_path`，最终输出 `/NAV_CMD` 到机器狗底盘。

产品平台第一阶段可以写一个 ROS 2 适配节点，把平台航点按顺序转换为 `/clicked_point`。但正式产品更建议新增结构化的 `ExecuteMission.action`，提供任务 ID、地图 ID/版本、当前航点、暂停、取消、进度和错误码。

**问：航点坐标有什么要求？**

答：航点必须属于当前激活地图的 `map` 坐标系。地图切换后，即使同样是 `(5, 8)`，实际物理位置也可能完全不同，所以旧地图的任务必须失效或重新绑定。目标还必须位于 2D 栅格的已知自由空间；当前规划器设置 `allow_unknown: false`，落在未知区或障碍区会规划失败。

## 七、产品功能还缺什么？

**问：当前代码已经支持平台上传和下发地图了吗？**

答：没有。当前只支持本地 GUI 选择地图目录，并把目录传给 ROS 2 Launch。没有发现业务 HTTP、MQTT、WebSocket、gRPC 等地图服务，也没有地图版本、上传、下载、校验、激活、回滚和任务审计功能。

**问：要实现产品需求，建议增加哪些模块？**

答：建议拆成四部分：

1. **地图管理服务**：接收地图包上传，保存 Manifest、文件哈希、版本和兼容信息。
2. **B 狗侧 Map Manager**：下载、校验、暂存、检查 M20 硬件与标定兼容性、激活和回滚地图；统一管理定位/导航进程。
3. **任务服务**：任务必须绑定目标机器狗 ID、地图 ID 和版本，保存航点、速度、循环策略和到点容差。
4. **ROS 2 平台适配节点**：把平台任务转换为当前 ROS 2 航点接口，并结构化回传定位、规划和执行状态。

建议状态流：

```text
queued
  -> downloading
  -> verifying
  -> staged
  -> activating
  -> active
```

失败时应进入 `failed` 并支持 `rollback`。

**问：切换地图时能直接覆盖文件吗？**

答：不能。安全切图至少要：

1. 拒绝新任务。
2. 暂停或取消当前航点序列。
3. 清空 `/global_path` 和 `/local_path`。
4. 持续向底盘发送零速度。
5. 停止导航和定位节点。
6. 校验并原子切换地图目录。
7. 重启 2D/3D 定位。
8. 等待 `/map`、`/map_2d` 发布成功。
9. 等待 `/localization_status=true`。
10. 再允许下发任务。

当前代码没有真正的热切图机制，第一版产品应采用“受控停止并重启定位/导航”的方式，不应宣传无缝切图。

## 八、有哪些重要风险？

**问：建图输出目录有什么危险？**

答：`lidar_loop_node` 启动时会清理目标目录中的旧地图文件，包括 `*.pcd`、`*.pgm`、`*.yaml`、`*.txt`、`*.bin`，并删除重建 `Scans/` 和 `Image/`。因此：

- 不要把 Bag 目录作为建图输出目录，否则可能删除 `metadata.yaml` 和其他文件。
- 不要在唯一生产地图目录中开始新建图。
- 每次建图使用新的版本目录。
- 平台传入的路径必须严格限制，当前 C++ 代码使用 shell 命令拼接路径，不应允许空格、分号或其他 shell 字符。

**问：A、B 都是 M20，标定参数还会影响地图下发兼容性吗？**

答：会。同型号不代表每台设备的实际标定完全一致。地图生成和定位依赖相机内参、相机—雷达外参、IMU—雷达外参、雷达—车体外参、时间同步和传感器模式。A 狗地图中的几何与描述符由 A 狗传感器系统产生；B 狗在线观测由 B 狗自己的传感器系统产生。两者偏差过大时，B 狗可能无法冷启动重定位，或虽然短时定位成功但持续跟踪有系统误差。Manifest 应保存 A 狗建图配置哈希和兼容配置版本，B 狗激活前应检查自身配置，并以现场重定位测试作为最终准入条件。

**问：人工修改 PGM 后还可以导航吗？**

答：可以，但要保证图像尺寸、分辨率和原点一致。人工修补 PGM 只影响 Nav2 的 2D 规划障碍，不会同步修改 3D ICP 地图。若 2D 与 3D 地图差异过大，可能出现“定位认为可达、规划认为不可达”或相反的情况，应进行仿真和实机验收。

**问：地图生成完成的判断是什么？**

答：不能只看 Bag 播放结束，也不能只看某个 PCD 出现。当前最终地图在建图后端节点退出的析构阶段生成。正确判断应包括：

- 建图后端正常停止。
- `map_3d.pcd` 和 `map_2d.pgm/yaml` 保存成功。
- `sc_database.txt` 帧数大于 0。
- 所有必需文件哈希计算成功。
- 3D 定位测试通过。
- 2D Map Server 和 `/map_2d` 测试通过。
- 实际导航规划测试通过。

**问：是否存在值得注意的代码缺陷？**

答：有几项产品化前应处理：

- 地图目录缺少 Manifest 和版本信息，无法溯源到具体楼层或 Bag。
- 导航按钮主要按 GUI 模式解锁，没有严格等待真实定位成功。
- `aruco.landmarks_file` 存在开发机绝对路径默认值，可选 ArUco 地图部署可能失效。
- `visual_descriptors.bin` 是 C++/OpenCV 原始二进制格式，需要明确格式版本和跨架构兼容策略。
- 当前任务状态使用字符串话题，缺少任务 ID、可靠应答、错误码和幂等语义。
- 地图目录清理由 shell 命令完成，路径输入需严格约束，长期应改成 `std::filesystem`。

## 九、代码库是怎么启动的？

**问：这个代码库的主要启动方式就是 `python3 -u robot_console/robot_console/app.py` 吗？**

答：是，这是 README 和现有代码对应的主要 GUI 启动入口。建议完整命令为：

```bash
cd /home/ubuntu/Desktop/ROS2_szs/DeepRobotics_ws
source /opt/ros/humble/setup.bash
source install/setup.bash
python3 -u robot_console/robot_console/app.py
```

`app.py` 本身不是 SLAM 算法节点，它是 PyQt 控制台和 ROS 2 编排入口：

```text
app.py
  -> QApplication
  -> RobotMainWindow
  -> Ros2BackendThread
  -> GUI 按钮通过 QProcess 执行 ros2 launch
```

主要按钮对应：

- 单次建图：`fast_livo frontend.launch.py` + `mapping backend_mapping.launch.py`。
- 3D 定位：FAST-LIVO 前端 + `backend_localization_3d.launch.py`。
- 2D 定位：FAST-LIVO 前端 + `backend_localization_2d.launch.py`。
- 2D 导航：`ros2 launch move navigation.launch.py`。
- Bag 回放：`ros2 bag play ... --clock`。

这些底层 Launch 也可以脱离 GUI 手动启动。因此 `app.py` 是当前主要产品交互入口，但不是算法唯一入口。

**问：为什么必须先进入工作空间目录再启动？**

答：当前 GUI 的工作空间识别在非标准目录布局下会回退到 `os.getcwd()`。如果从其他目录直接执行绝对路径形式的 `app.py`，可能得到错误的工作空间路径。最稳妥方式是先 `cd` 到项目根目录。

## 十、针对“A 狗 3 楼地图下发给 B 狗”的落地建议

**问：把 A 狗生成的 3 楼地图下发给同为 M20 的 B 狗，最小可行方案是什么？**

答：可以按以下阶段推进：

1. 使用 A 狗录制的 `bag_20260607_173905` 在独立目录生成一套新地图。
2. 人工检查 3D 点云、2D 栅格、回环轨迹和地图原点。
3. 记录 A 狗 M20 硬件配置、设备参数、标定摘要和软件版本。
4. 先用 A 狗验证该目录的 3D 定位、2D 定位和 Nav2 路径规划。
5. 生成 `manifest.json`，计算全部必需文件 SHA-256，并声明允许部署的 M20 配置版本。
6. 将完整目录压缩上传到平台，并标记为“浙大 3 楼 / A 狗建图”。
7. B 狗下载到版本化暂存目录，校验文件并比较自身雷达、摄像头、IMU、外参和软件配置。
8. B 狗停止任务、定位和导航，原子切换 `current` 地图。
9. B 狗启动 2D/3D 定位，在 3 楼多位置、多朝向验证重定位和地图对齐。
10. B 狗定位稳定后，平台下发绑定 `targetRobotId=B` 和该地图版本的 `map` 坐标航点。
11. B 狗低速执行并回传定位、规划、控制和任务状态；验收通过后再将该地图标记为 B 狗生产可用。

当前代码可以完成 A 狗 Bag 建图、本地地图检查、A/B 狗本地定位验证和本地航点执行；Manifest、平台上传下载、跨狗兼容性自动判定、版本切换和结构化任务接口需要新增开发。

**问：产品验收时最关键的检查项是什么？**

答：至少包括：

- 地图包文件完整且哈希一致。
- 地图能明确追溯到楼层、来源 Bag、A 狗 ID、A 狗设备标定和版本。
- A、B 两狗均为声明兼容的 M20 硬件配置，B 狗自身标定已完成并通过兼容检查。
- B 狗激活的是任务绑定的同一地图版本，任务的目标机器狗 ID 也是 B。
- 2D/3D 地图和重定位数据库来自同一次建图。
- B 狗使用自身设备参数运行前端，没有直接套用 A 狗的个体标定参数。
- B 狗在 A 狗地图中完成多位置、多朝向重定位实测。
- 定位未成功时拒绝导航任务。
- 切图期间底盘保持零速度。
- 任务点位于 `map` 坐标系已知自由区。
- 下载中断、校验失败和激活失败可回滚。
- 旧地图任务不能在新地图上继续执行。
- 机器狗重启后能恢复当前激活地图，但不应自动恢复未确认的运动任务。
